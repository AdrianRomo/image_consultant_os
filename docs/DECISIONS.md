# Decisions

- 2026-09-28 — Repo layout: `web/` (Next.js 16 App Router, TS, Tailwind 4). `api/` deferred to Phase 3.
- 2026-09-28 — Phase 0 (consultant interview) NOT yet done. Phase 1 started early on synthetic data at the owner's request. `WORKFLOW.md` / `PRODUCT.md` are still to be written after the interview; treat Phase 1 output as provisional.
- 2026-09-28 — Concept routes use neutral labels (Concept A/B/C) so the consultant sees no implied favorite. Key: A = Editorial fashion, B = Quiet luxury, C = Contemporary studio.
- All client data in `web/src/lib/fixture.ts` is fictional; portrait is a synthetic SVG placeholder.
- 2026-09-29 — Visual elevation pass. Chapters of the client story reordered so *advice precedes craft* (Identity, Presence, Assessment, Opportunities, then Colour, Silhouette, Wardrobe, Looks, Evolution), each with an editorial title and a plain-language name. Why: the consultant opening a profile must see what to do next without scrolling through styling material.
- 2026-09-29 — Colour analysis is shown as a position between two poles (`Spectrum`), never as a score. Why: plan §4 forbids arbitrary numeric scores; a rating-dot row read as one.
- 2026-09-29 — No scroll-triggered animation and no page curtain. Motion is limited to four durations (160 / 260 / 300 / 520ms) and only for continuity, hierarchy, feedback or spatial relationship. Shared portrait uses the View Transitions API (Chromium-first, falls back to a plain page change).
- 2026-09-29 — Controls are native elements restyled once (`ui/controls.tsx`, `ui/Overlay.tsx`); no shadcn/Radix/Base UI dependency was added. Why: the identity must not drift toward a library default, and the app needed none.
- 2026-09-29 — Copy for reusable dossier patterns comes from `lib/copy.ts` (EN/ES); domain enums are keys, not display text. The rest of the product is still English-inline until the pilot language is chosen.
- 2026-09-29 — The page carries no texture; photographs share one visible grain-and-falloff finish (`.photo`). The old page-wide grain measured ±1/255 (imperceptible) and cost a full-viewport blended layer.
- 2026-09-29 — Studio hero copy ("Your image, considered.") kept: it reads as the studio's own tagline and the hero composition was to be preserved.
- 2026-09-29 — Portraits are now **credited free-licence stock photographs** graded into the palette (`docs/IMAGE_CREDITS.md`), replacing the illustration. They are examples: the client is fictional, and the "direction" photograph is a *reference* (a different person), labelled Today / Reference, never her result. Swapping in a consented photograph is one file (`lib/photos.ts`) plus re-tuning `observationMarkers`. Why: the brief treats photography as a first-class primitive and an illustration could never carry it. Open question for the owner: whether stock faces should appear at all outside your own circle.
- 2026-09-29 — The product's CSS classes live in `@layer components` so Tailwind utilities win (`DESIGN.md` §8). Motion, reduced motion, dialogs, focus and view transitions stay unlayered on purpose. Verified by pixel and computed-style diffs.
- 2026-09-29 — On phones the assessment portrait becomes a sticky 2:1 "focus window" that pans and zooms to the open observation, instead of a connector line.
- 2026-09-29 — Spanish for the whole product is deferred until the pilot language is chosen with the consultant (plan §4); only the dossier patterns are dictionary-driven.

- 2026-09-29 — Recommendations answer **two separate questions**: workflow (Draft, Awaiting review, Approved) and visibility (Consultant only, Shared with the client). Only an approved recommendation can be shared; approving does not share; a shared one must be withdrawn before it is reopened. `lib/workflow.ts` is the single definition and its tests enumerate every state and action. Why: "awaiting review" and "the client can see it" were one word before, and a consultant must never wonder which of them she is looking at.
- 2026-09-29 — The client's page is **built from a whitelist, not filtered from the consultant's records** (`lib/share.ts`), lives in a `(share)` route group with none of the studio's chrome, and renders the same component the consultant previews. Why: hiding with CSS or a client-side flag still sends the data; the ⌘K search lists every client. Verified by scanning everything the browser receives (`docs/audit/scripts/share-boundary.js`), including a run with every recommendation shared.
- 2026-09-29 — Changes are held in **server memory** (`lib/store.ts`), not a database, and reset when the server restarts. Why: there is no database yet (plan §5), the pilot is on synthetic data, and adding storage would have meant an infrastructure change to the sandbox. The store has the interface a database needs (list, one guarded move), so replacing it touches one file. **The write endpoint has no login**, like the rest of the app; see `DEPLOY.md` before exposing it.
- 2026-09-29 — The studio has a **fixed fictional "today"** (14 March 2026, `lib/clock.ts`) so "in 3 days" and every logged date agree with the fixture. Replace with the real clock when the fixture is replaced by real records.
- 2026-09-29 — "Today in the studio" shows only what the records say: appointments (nearest first, days to go), recommendations awaiting review, and one next action chosen by a stated rule (a recommendation waiting on a decision, highest priority first; otherwise the nearest appointment; otherwise nothing). Diego's "analysis ready" is shown as information, never a link: his dossier is not built.
- 2026-09-29 — **The comparison is of wording, and says so.** Looks and the client's direction have no history in the data, so they have none. The one recommendation with an earlier version (rec-1) uses a small synthetic history added to the fixture; a real product must record a version whenever wording is saved.
- 2026-09-29 — Tests run with `node --test` and a 10-line TypeScript loader (`web/scripts/`) that uses the `typescript` package already installed. Why: this workstation's Node is built without native type stripping, and a test framework was not worth a dependency for a few hundred lines of pure logic.
- 2026-09-29 — Garments stay vector illustrations. The only licensed photographs in the repo are the two portraits, and the jacket-detail crop is of the *reference* person's jacket, never her Ink blazer, so it must not stand in for a garment. The wardrobe gained relations (looks, worn with, related advice) and a true-colour chip instead.

- 2026-10-06 — **AI garment preview is a provisional experiment, run offline and locally** (`experiments/garment-preview/`), like Phase 1: stock or synthetic photographs only, no endpoint, nothing in the web app yet. The audience is one consultant and her client. Why: the plan lists AI-generated outfits under "do not block the pilot" and treats AI on photos as a separate opt-in (§4, §5); Phase 0 is still not done. Originals stay on the workstation; Cloudflare R2 for stored photos is a later stage, behind a `PhotoStore` interface, and needs login and consent first.
- 2026-10-06 — **The face guarantee comes from the pipeline, not from a model.** The edit mask is the garment minus the person (face, hair, skin, glasses, jewellery, hat, bag, each with a safety margin), the colour change is deterministic Lab arithmetic (no generative model), and a separate check on the saved lossless PNG proves nothing outside the mask changed. Any later generative step (fabric) must be composited back through the same mask and pass the same check. Why: instruction-based editors regenerate the whole frame and can drift a face even when told not to.
- 2026-10-06 — Colour is judged by the garment's **median colour against the swatch** (dE2000 limit 4), calibrated in a loop. The preview is an idea simulation labelled as such, never evidence for the colour analysis: it cannot show reflected colour on skin.
- 2026-10-06 — **A passing check is not a correct mask, so a person reviews every preview before a client sees it.** On 24 stock photographs the face and skin were never altered, but only 14 masks were usable as they stood; 8 recoloured an inner layer too (blazer plus shirt) and 2 were wrong outright, and every one of them passed the label-based checks. A mixed-colour flag catches most (8 of 10) but is tuned on the same photographs. Consequences: previews join the existing Draft / Review / Approved workflow, the consultant must be able to choose which layer to recolour, and photos must contain one person. Evidence: `experiments/garment-preview/corpus.md`.
